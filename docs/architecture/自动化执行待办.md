# PRD + UI 自动化执行待办（执行级）

> 目标：用于一次触发后可直接逐项执行与勾选。

## 0. 环境检查

- [ ] 0.1 检查 Node.js 版本满足 `>= 22.22.0`。
- [ ] 0.2 检查 pnpm 版本满足 `>= 10.32.0`。
- [ ] 0.3 若版本不满足，停止执行并提示升级。

## 1. 输入准备

- [ ] 1.1 确认 `docs/prd/` 目录存在。
- [ ] 1.2 确认 `docs/ui/` 目录存在。
- [ ] 1.3 扫描 `docs/prd/` 下所有 sprint 子目录中的 `.md`（排除 `README.md`）。
- [ ] 1.4 按执行顺序排序：先 sprint 目录名，再 PRD 文件名。
- [ ] 1.5 检查 PRD 文件编码与 frontmatter 格式可读。
- [ ] 1.6 对每个 PRD 解析 `figma_links` 与 `screenshots` 字段。
- [ ] 1.7 校验 `screenshots[].path` 为相对 `docs/` 的可解析路径（如 `ui/sprint1/xxx.png`）。
- [ ] 1.8 生成“sprint / PRD / 设计源”映射表（`figma_links`、`screenshots`、兜底）。
- [ ] 1.9 以 PRD 文件名（不含 `.md`）作为 `<prd-name>`，用于后续产物命名。

## 2. 意图与范围确认

- [ ] 2.1 识别用户输入是否命中 PRD+UI+实现意图。
- [ ] 2.2 判定任务类型为“自动实现链路”。
- [ ] 2.3 写入任务唯一 ID（全流程追踪）。
- [ ] 2.4 输出本轮任务范围（本次处理哪些 PRD）。

## 3. OpenSpec 阶段（每个 PRD）

- [ ] 3.1 创建/选择 `change-id`（动词前缀 + kebab-case）。
- [ ] 3.2 执行 Proposal（逻辑命令 `openspec proposal`）。
- [ ] 3.3 生成 `proposal.md`（Why/What/Impact）。
- [ ] 3.4 生成 `tasks.md`（可执行清单）。
- [ ] 3.5 生成 `spec delta`（ADDED/MODIFIED/REMOVED）。
- [ ] 3.6 若复杂变更则生成 `design.md`。
- [ ] 3.7 执行 `openspec validate --strict`。
- [ ] 3.8 校验失败时修复后再次验证。
- [ ] 3.9 Proposal 通过后默认确认进入 Apply（除非用户明确拒绝）。
- [ ] 3.10 执行 Apply（逻辑命令 `openspec apply`）并按 `tasks.md` 逐项实施。

## 4. 设计分析阶段（每个 PRD）

- [ ] 4.1 若 `figma_links` 有效（至少 1 条有效 URL），直接走 Figma MCP，并跳过截图匹配。
- [ ] 4.2 若无有效 `figma_links`，按 `screenshots` 配置读取截图并进入截图分析模式。
- [ ] 4.3 若 `screenshots` 缺失或无效，在同 sprint 下按 PRD 文件名前缀兜底匹配截图。
- [ ] 4.4 若兜底仍失败，标记 `UI_PENDING`，继续后续流程。
- [ ] 4.5 多 `figma_links` 场景按列表顺序分析，并合并为同一个 PRD 分析清单。
- [ ] 4.6 提取文字、图片、布局、层级四要素并输出分析结论。
- [ ] 4.7 产出 UI 分析清单：`docs/样式还原/<sprint>/<prd-name>-UI分析清单.md`。

## 5. 代码实现阶段（每个 PRD）

- [ ] 5.1 根据 PRD 语义拆分路由与组件边界。
- [ ] 5.2 创建/更新路由目录（Page/Loader/index.module.scss）。
- [ ] 5.3 创建页面级组件与通用组件。
- [ ] 5.4 完成接口类型定义（interfaces）。
- [ ] 5.5 完成接口封装（http）。
- [ ] 5.6 如需全局状态，创建 Pinia store。
- [ ] 5.7 样式全部使用主题变量与模块化样式。
- [ ] 5.8 接口未就绪时启用 mock 并标注替换点。
- [ ] 5.9 命中高风险操作时触发人工确认。

## 6. 质量门禁阶段（每个 PRD）

- [ ] 6.1 TypeScript 类型检查通过。
- [ ] 6.2 ESLint 检查通过。
- [ ] 6.3 关键路径单测通过。
- [ ] 6.4 关键页面冒烟测试通过。
- [ ] 6.5 E2E 测试通过。
- [ ] 6.6 构建（Vite build）通过。
- [ ] 6.7 若失败，自动修复并重试（最多 2 次）。
- [ ] 6.8 超过重试上限则标记该 PRD 失败并继续下一个。

## 7. UI 验收阶段（每个 PRD）

- [ ] 7.1 按设计源优先级执行验收：`figma_links` > `screenshots` > 同 sprint 前缀兜底截图。
- [ ] 7.2 记录 UI 问题清单（P0/P1/P2）：`docs/样式还原/<sprint>/<prd-name>-UI问题清单.md`。
- [ ] 7.3 修复阻断级 UI 问题并回归验证。
- [ ] 7.4 允许少量非阻断问题并明确留档。

## 8. 汇总与交付阶段

- [ ] 8.1 汇总每个 PRD 的通过/失败状态（含对应 sprint 维度）。
- [ ] 8.2 汇总 `UI_PENDING` 项与待替换 mock 清单。
- [ ] 8.3 汇总风险项与处置建议。
- [ ] 8.4 每个 PRD 验收通过后执行 `openspec archive <change-id> --yes`。
- [ ] 8.5 归档后执行 `openspec validate --strict`。
- [ ] 8.6 生成执行日志记录（含任务 ID、关键节点与重试次数）。
- [ ] 8.7 输出“上线就绪结论”（不含部署）。
- [ ] 8.8 输出后续部署前检查建议。
